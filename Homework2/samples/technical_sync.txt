Технічний синк — Архітектура мікросервісів
Учасники: Богдан (архітектор), Соломія (DevOps), Роман (бекенд), Наталя (безпека)

Богдан: Переходимо до нової архітектури. Зараз монолітний Django-бекенд, хочемо розбити на мікросервіси. Перший етап — виокремити auth-сервіс.

Роман: Якщо виносимо auth — треба JWT з refresh-токенами. Я можу написати auth-мікросервіс на FastAPI. Дедлайн реальний — 22 травня.

Богдан: Добре, Романе — auth-мікросервіс на FastAPI з JWT, до 22 травня.

Соломія: Для деплою будемо використовувати Kubernetes. Мені треба підготувати Helm-чарти для нових сервісів і налаштувати Istio service mesh для inter-service communication.

Богдан: Соломіє, Helm-чарти + Istio конфігурація — яки строки?

Соломія: Helm-чарти зроблю до 19 травня. Istio — це складніше, думаю до 25 травня.

Богдан: Окей. Наталю, що по безпеці?

Наталя: Треба провести threat modeling для нової архітектури і впровадити mTLS між сервісами. Також rate limiting на API Gateway. Можу зробити threat model до 18 травня, а mTLS налаштування разом з Соломією — до 25 травня.

Богдан: Добре. Рішення по архітектурі: переходимо на event-driven через Kafka для асинхронної комунікації між сервісами. PostgreSQL залишається основною БД, але кожен сервіс матиме свою схему. Redis для кешування і сесій. API Gateway — Kong. Всі зовнішні API через HTTPS, внутрішні — через mTLS.

Роман: А що з моніторингом?

Богдан: Prometheus + Grafana, Соломія підніме стек. Соломія, моніторинг стек до 28 травня?

Соломія: Так, зроблю.

Богдан: Підсумовую рішення: event-driven через Kafka, PostgreSQL per-service schema, Redis для кешу, Kong як API Gateway, mTLS для internal traffic, Prometheus+Grafana для моніторингу.
